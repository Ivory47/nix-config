## 8. Status bar and background blur architecture
**Global switch: `Theme.glass`** (`shared/Theme.qml`, default true in `ThemeDefaults.qml`). It feeds `glassEnabled` of the bar's and both popups' `GlassBackdrop`. False: no capture request, no pipeline (checked: 0 requests, 0 updates), the bar is its plain translucent rectangle (`StatusBar.qml`), the popups a plain opaque tinted panel (`GlassPanel.alpha` is 1 when `glassEnabled` is false; `glass.frag`'s no-backdrop branch draws the row highlights too), and `GlassPopup` shows its content at once instead of waiting for a capture. Needs `hms` and `qsr`. `setGlass` over IPC still toggles one instance at runtime for measuring.

**Clean mode (Lucent plugin loaded, `GlassBackdrop.clean`).** The compositor leaves this process's layer surfaces out of its captures, so steps 2 below are skipped: `shaders/clean.frag` replaces the unmix (the capture cropped to the region is the background), `shaders/flag0.frag` replaces the statistics pass (one texel, "all good"), no ring snapshots are taken, the tag pixel is not needed, and `GlassPanel.alpha` is 1 (opaque glass: no leak, so nothing to cancel). `clean` = `LucentStatus.active && cap.wholeOutput && !cap.dmabufBroken`: the plugin handles whole-output (monitor) captures only, so a region capture (the shared-memory fallback) automatically uses the old path. `LucentStatus` (`shared/LucentStatus.qml`) reads the marker file `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/lucent-active` that the plugin writes (polled every 3 s; the directory is new for every Hyprland start, so a stale marker is impossible). **There is no setting to turn clean mode off**: with the plugin loaded every Quickshell capture is clean and the unmix cannot work on one; unload the plugin (remove the load in `hyprland.lua`) to go back. IPC `glass stats` has `pipeline.clean`.

Wiring: `status-bar/StatusBar.qml` contains `GlassPanel` and a one-pixel `GlassTag` (both inside `barContent`) and a sibling `GlassBackdrop { composite: barContent; blurRadius: Theme.glassBlurRadius; ipcTarget: "glass" }`.

Pipeline (`shared/glass/`; read from code, with the behaviour below measured on the laptop, 1920x1080 at scale 1.333, Hyprland 0.56):
1. **Acquire:** `GlassCapture` (`native/glasscapture.cpp`) uses `zwlr_screencopy_manager_v1` `copy_with_damage` into GBM dmabufs (EGLImage import, wl_shm fallback). Whole output is captured by default (works around a Hyprland per-region session leak at fractional scales; the shader crops the bar region). One request in flight, started as soon as the one before is answered (no pacing of our own unless `minInterval` is set: `copy_with_damage` is answered at most once per output commit); a sampled duplicate check (`sameAsBefore`: the green channel of every 8th pixel of every row of the region, the start shifted from row to row so that a moving edge cannot pass between the samples; every 32nd for a full-output region, at most 65536 samples; compared with the last published capture) drops unchanged captures. A published capture is rendered at once (`deliverUpdateNow`), not at the surface's next frame callback. A capture is new if one sample moved by more than 3 levels, or if at least 10 samples (1% if more) moved by 1 or more; the second rule catches slow, faint changes such as a wallpaper fade. This is what keeps an idle desktop quiet: about 2.5% CPU, no updates.
2. **Remove the bar from its own capture:** `unmix.frag`: `bg = (capture - own.rgb) / (1 - own.a)`. `own` is the bar as it was in the frame the compositor captured, which is not always the latest one. Every presented version of the bar is kept in a ring of 8 snapshots (`r0..r7` in `GlassBackdrop.qml`, one taken per update), and one opaque pixel at the top left of the bar (`GlassTag.qml`, blue = 46 + 4 * (version % 8), green 30, red per instance: bar 30, launcher 34, clipboard 38, `GlassBackdrop.tagRed`) tells the shader which version a capture holds (the compositor copies opaque pixels exactly). A capture whose tag is not ours, or not kept, is rejected (except for a popup that is closed or opening: it sets `absentTagRed: 30`, and the bar's tag at the tag's place then means its surface was not in the frame, so the capture is taken as the background as it is, section 9). `settle.frag` keeps the previous background when a capture is rejected (more than 1% of pixels wrong, or more than 60% unknown).
3. **Blur:** `blur.frag`, separable Gaussian via `GlassBundle.qml` (full to half size, then vertical at half size; RGBA16F; max 48 taps/side).
4. **Present:** three `GlassBundle`s are rotated. `process()` builds the update into the bundle that is not on screen and shows it at once: the frame that renders it also draws the glass with it (Qt renders what a texture needs before the item that samples it). `readIdx` is the bundle on screen, `prevIdx` the one before it (`last`: what is kept on rejection, and the unmix's `previous`). A capture that arrives before the previous update was synchronised is folded into it (`scheduledAt`). `GlassPanel` + `glass.frag` draw refraction (bottom edge), dispersion, tint, shine. The glass draws with alpha 0.92 (`GlassStyle.alpha`) and subtracts the leak of the background it estimated.
5. **Refresh:** event-driven (compositor damage and frame swaps). Measured with the latency probe (section 5) and a background that changes every frame: 59-60 captures, updates and window frames per second (one frame per update, see "A scheduled `ShaderEffectSource` update" below); probe CPU 18% (bar-sized) / 24% (full output) before that fix, Hyprland 18%. Idle: no updates.
6. **Latency:** one compositor frame (16.7 ms at 60 Hz), which is the floor of this design: the compositor frame that has the change answers the capture (it reaches us 5.5-7.5 ms after the commit, when the GPU has finished), we render the update (1.5-2 ms to our commit), the next compositor frame shows it (5-7.5 ms to spare). With the probe, 96.7% (bar-sized) and 100% (full output) of the frames of a moving background reached the glass in the next frame; the rest are captures that arrive too late for it (a busy GPU). Before the three fixes below it was 76% and 82%, the others 2 or 3 frames late or never updated. Zero lag needs the blur in the compositor, or the compositor waiting for our commit before it renders (neither is done).

Hyprland / independence: `hyprland.lua` has no `layer_rule` for `statusbar`; no `ext-background-effect` or toplevel-export protocols are used, so the blur is computed entirely in the shell. Hyprland's global `decoration.blur` is enabled (`hyprland.lua:~145-150`) but affects only window content seen in the capture. Requires wlr-screencopy + dmabuf from the compositor; code is tuned to Hyprland 0.56.x behaviour.

Lessons that cost time (all verified by experiment on the desktop; keep these in mind when changing `shared/glass/`):
- **Hidden `ShaderEffectSource`s are rendered lazily.** Qt rendered a non-live, hidden source only when something visible sampled it. Updates of a bundle that was not shown waited until it was shown and were then rebuilt while shown (the bar flashed plain tint, then noise, then magenta in a marker experiment), and the ring snapshots would never render. The keep-alive consumer in `GlassBackdrop.qml` (one tiny off-window `ShaderEffect`, `shaders/keepalive.frag`, sampling all 14 scheduled textures; its output must depend on every sampler or the unused ones are optimised away) makes scheduled updates render. Do not remove it.
- **A capture must be unmixed against the bar version it holds.** The compositor can answer with the bar as it was one or two frames earlier, and the glass changes with every update. Without the tag, rejection during a window drag was about 82% with overlapping captures, about 48% with captures held until the new glass was presented, 0% with two frames of margin, but only about 15 updates per second that way. The tag and the ring give about 54 per second with nothing rejected. (A "best matching candidate" selection by counting wrong pixels cannot work: the range test cannot tell similar versions apart.)
- **Texture cycles:** a bundle must never read its own output (`kept` is `draftSource` for the previous bundle), and the unmix's `own` sampler for the ring slot rendered in the same frame is swapped for another slot (otherwise the snapshot would wait for the unmix and the unmix for the snapshot).
- **Three things made the blur trail** (branch `fix/hyprland-blur-latency`; found with the latency probe, laptop, clean mode; the earlier flip test in Lucent's tools changes the background once and then waits, so it showed none of them). Share of the compositor frames of a continuously moving background, bar-sized probe, before the fixes: (1) 12-13% of the captures were **dropped as duplicates although the background had changed**: the check sampled the same columns on every row, 61 pixels apart, so a vertical edge moving sideways was not seen until it crossed a column (38% dropped with a single moving bar; the glass then lags by up to 61 px and catches up in jumps). Now a staggered lattice (step 1 of the pipeline). (2) 4-8% of the frames were **never captured**: the next request was held back until one refresh period after the START of the previous one (a whole-millisecond timer on top), a median 3 ms and up to 11 ms after the answer, and reached the compositor after its next commit. Now requested at once. (3) 1-4% of the updates **waited for the surface's frame callback**: Qt (`QWaylandWindow::requestUpdate`) does not deliver an update request while a frame callback is outstanding, Hyprland sends the callback when it renders its next frame, so the update was rendered just after the frame it belonged in (and the late commit's own callback was then outstanding when the next capture came). Now `GlassCapture::deliverUpdateNow()` delivers the pending request when a capture is published; it relies on `QSG_NO_VSYNC=1` from the wrapper in `default.nix` (with vsync Qt's swap would wait for the callback instead). When measuring, count published captures, not capture answers: an answer that is dropped as a duplicate looks like an update that never came. Deployed (`hms`, `qsr`) and checked in the real shells over the moving test background: status bar, launcher, clipboard and settings each 60 captures, 60 published and 60 updates per second, no duplicates, no failed or waiting captures (bar CPU 20%, launcher and clipboard 27%, settings 37%); idle bar: no updates, 0.6% CPU. NOT checked: a real window dragged or resized by hand, workspace-switch animations, the estimating pipeline without the plugin (same code path for all three fixes, but not run), the desktop, other refresh rates, several monitors.
- **A scheduled `ShaderEffectSource` update costs a second frame unless told otherwise** (branch `fix/glass-double-render`). Qt connects the source's texture (a `QSGLayer`) to the item: `connect(m_texture, SIGNAL(updateRequested()), this, SLOT(update()))` in `QQuickShaderEffectSource::ensureTexture`. The layer emits `updateRequested` on the render thread during the scene synchronisation (`QSGRhiLayer::scheduleUpdate` and `markDirtyTexture`), the item's `update()` runs on the GUI thread after that synchronisation, and Qt renders and commits the whole window once more with the same content: about 120 window frames for 60 glass updates per second (8 such requests per update in the render-loop log, `--log-rules "qt.scenegraph.renderloop.debug=true"`). The request is only needed for a texture that gets dirty on its own (live or recursive sources); a scheduled update is rendered by the frame that `scheduleUpdate()` itself asked for. `GlassCapture.scheduledOnly(source)` removes that one connection (the texture's connection to its texture provider, which is what passes "changed" down the chain of passes within the frame, stays), on the render thread and again whenever the source gets a new texture; `GlassBackdrop` registers every source of the pipeline (`draftSource`, `flagSource`, the counters, the ring, `GlassBundle.sources`). A new `ShaderEffectSource` in the pipeline must be added to that list, and must not be live. Measured with the probe, before and after: window frames per second 120 to 60 at 60 updates; probe CPU 25% to 20% (bar-sized) and 34% to 27% (full output), GPU 3.1% to 2.6% and 31% to 26% (with `WAYLAND_DEBUG` logging, which makes the CPU numbers higher than in normal use); the glass on screen follows as before (moving bar with `lagcap`, median 26-27 ms before, 24-25 ms after); a blur radius change with captures stopped is one window frame and changes the picture; with the estimating pipeline forced (`clean: false` in a scratch copy) 121 to 61 window frames, ring versions advancing (the picture of that pipeline was NOT checked: the captures were clean ones). Deployed and checked in the real shells over the moving test background: window frames per second 120 to 60 (status bar, settings) and 121 to 63 (launcher, clipboard: the text cursor blinks), all at 60 updates, nothing failed; bar CPU 20% to 17%; the popups' CPU was not clearly lower in that run (launcher 27% and 29%, settings 37% and 35%, measured a day apart).
- **The duplicate check must be sensitive to faint changes.** The glass covers the background (alpha 0.92: only 8% of it shows in the capture, 12% at 0.88), so a background change of N levels moves a capture sample by about N/12. With the original rule (any sample by more than 3) a slow `awww` wallpaper transition needed about 40 levels of change before it registered: measured over a transition, about 200 captures arrived and only about 8 were published (at most 5 per second). With the 1%-of-samples rule a transition publishes bursts of 50-100 captures (up to 51 per second) and an idle desktop still publishes nothing. Raising `GlassStyle.alpha` lowers the sensitivity further.
- **The validation counters read back through `grabToImage` (`decode()`, `readout.frag`) are partly corrupt** (wrong-frame and unusable were identical, "held last good" went negative, "valid backdrop seen" stayed false, "last" percentages exceeded 100%). Trust accepted / rejected totals loosely, and the capture counters (`requests`, `published`, `duplicates`, `frames`) and CPU numbers. The counting pass now runs only while diagnostics are on; `measure.py` turns diagnostics on, so its bar CPU is a little higher than in normal use (use per-thread `/proc` samples for that).
- `measure.py` restores the normal settings in a `finally`; it measures CPU only (no GPU, memory or power). `perf` is not installed and `strace` cannot attach (`ptrace_scope` 1): per-thread CPU from `/proc/<pid>/task/*/stat` is the finest profile available.
- **Compare with Pleamar** (`github.com/k4ditano/pleamar`, Rust + wgpu; `marea-plm` is only an app built on it and has no blur code; BSD-3-Clause). Our pipeline is a port of its lens: `src/lens.rs` (`Lens::receive`, `Frost::run`), `src/blur.rs` (blur passes), `src/backdrop.wgsl` and `src/backdrop_check.wgsl` (unmix and judging), `src/platform/capture.rs`, `src/shape.wgsl`. Its duplicate check is the same as ours was (one byte in 13, tolerance 3), so it is not a source for faint-change detection. It differs in: region capture with a `reach` margin (we capture the whole output because of the Hyprland session leak), at most one capture per 50 ms, no tag or frame history (the surface waits for the screenshot, serialised), samples of pixels its own scene repainted are excluded from the comparison, an identical capture is taken in once more before being ignored, a capture is lost after 500 ms and a still-screen poll every 250 ms for a Hyprland quirk. `lens = image` uses a picture file as the backdrop instead of a capture. Read only as far as `lens.rs` lines 131-420 and its constants; its capture pacing, blur source and read-back were not read.
- Never put the string `quickshell -c status-bar` in a command run from Claude Code's shell: `reload.sh` uses `pkill -f` on it and kills the calling shell.
- **Test load without dragging a window:** a second Quickshell instance (`qs -p file.qml`, started and killed by PID) with a `PanelWindow { aboveWindows: false; exclusionMode: ExclusionMode.Ignore; anchors top/left/right; implicitHeight: 160 }` on the Bottom layer, under the bar, with a few coloured `Rectangle`s sweeping across with `NumberAnimation on x { loops: Animation.Infinite }`. Check with `hyprctl layers` that it is on the bottom layer; remove it afterwards. A first start once produced a static scene; check that `published/s` is near 54.

Constraints / known limitations:
- **Visible tag pixel (temporary, to revisit):** one real pixel at the top left of the screen changes by a few 255ths of blue per update. The alternative discussed: carry the tag in pixels that are opaque anyway (clock, workspace numbers, icons: shift their colour by a few 255ths and match opaque pixels per ring slot), or match timestamps (`wp_presentation`), which needs C++. The tag requires the bar at the top left of the output.
- Ring depth is 8 versions: a capture more than 8 updates old by the time it is unmixed would be unmixed against the wrong slot (not seen at 11-16 ms capture latency).
- Dividing by (1 - alpha) amplifies capture errors: 8.3x at 0.88, 12.5x at 0.92; the background cannot be recovered at all from 0.97 up. Background is unknown under opaque bar content.
- Text, clock or animation changes between updates are not in the ring: a few pixels mismatch until the next update (well under the 1% threshold).
- Popups/OSDs/notifications overlapping the bar region are captured as "background".
- Whole-output capture cost scales with resolution and monitor count; dmabuf pool up to 12 buffers per monitor (memory estimate unmeasured).
- Hardcoded: `origin` (0,0) (top bar only); `blurRadius` is `Theme.glassBlurRadius` (default 14); no output-transform handling seen; relies on Qt private APIs.
- Dead code: `shared/BackdropBlur.qml` (+ `Theme.backdropBlur`), `status-bar/glass-test/`, commented-out fade in `StatusBar.qml`.
- **GPU time** (measured on the laptop, Intel Tiger Lake iGPU, i915; render-engine time of the shell's own process from `/proc/<pid>/fdinfo` `drm-engine-render`, which excludes Hyprland's work; synthetic sweep load, about 50 updates/s, the worst case: nothing behind changing means no updates and no cost). Scratch copies with two extra IPC calls (`setBlur`, `setBlurPasses`) were used; they are not in the repo. Bar (1920x68 strip): 8.0% busy, 1.54 ms per update; with the two blur passes skipped 5.3% / 1.02 ms, so the blur is about a third (0.52 ms per update). Popup (full output 1920x1080): 29.5% busy, 5.96 ms per update; without the blur passes 17.2% / 3.39 ms, so the blur is about 43% (2.6 ms per update). Of the blur cost, about 30% is fixed (passes at 3 taps: bar 0.23 ms, popup 0.81 ms) and the rest grows with sigma until the 48-tap cap: bar 6.3% / 7.2% / 8.0% / 8.3% busy at `blurRadius` 0.1 / 7 / 14 / 28 (popup 20.8 / 26.1 / 29.5 / 32.4). The horizontal pass is at its cap from about 14.4 (it is already at radius 47 of 48 at 14); the vertical pass (half sigma) still grows, which is where the 14 to 28 difference comes from. The blur always runs at half resolution whatever the sigma; scaling the downsample with sigma is the untried way to make a larger blur cheaper. Clocks were not pinned: busy time is not work done.
- Still **UNKNOWN**: memory, power, multi-monitor behaviour, and behaviour at other scales. A rare colourful-noise frame was seen once while dragging, before the tag; not seen since, but unconfirmed.

## 9. Glass on the app launcher and the clipboard popup
Both are built from two shared components in `shared/glass/`; read their header comments before changing either popup:
- `GlassPopup.qml` — the full-screen overlay `PanelWindow` (Overlay layer, anchored on all sides, `exclusionMode: ExclusionMode.Ignore`, so the surface is at the output's top left, which the tag needs; with the bar's exclusive zone the surface started at y=51 and nothing worked). Everything the popup declares becomes a child of its `content` item (the surface the glass is computed for; it also holds the `GlassTag`), and a `GlassBackdrop` (`blurRadius: Theme.glassBlurRadius`, `ipcTarget: "glass"`, `active: shown`) is built in. It owns `shown`, `presented` (content visible), `hoveredItem`, `focusItem` (gets the keyboard), `tagRed`, `cancelAmount`, the open sequence / reveal/ramp logic and the keyboard-focus / input-mask handling. Signals `popupOpened()` / `popupClosed()` (not `closed`: Quickshell windows have one already). The instance sets `WlrLayershell.namespace`.
- `GlassListPanel.qml` — a `GlassPanel` with the popup look (`tint: Theme.background`, `tintStrength: 0.65`, `frost: 1.0`, all four edges bevelled) and the highlights of the search field, the selected row and the hovered row (`fieldStrength` 0.55, `selectedStrength` 0.7, `hoveredStrength` 0.5). Properties `popup`, `field`, `listView` (+ x, y, width, height of the panel in whole pixels). It must be a direct child of the popup's items, below the widgets.
**Foundations (2026-11, branch `feature/popup-foundations`, written but not yet run: needs `hms` + `qsr`).** `GlassPopup` also has: `openPopup()` / `closePopup()` / `togglePopup()` (+ `aboutToOpen()`), `closeOnWorkspaceChange` (default on), `ipcTarget` (a built-in `toggle`/`show`/`hide` handler), `closeOnOutsideClick` + `panelItem` (a click outside that item closes; unset = every click closes), and `exclusive` (one widget at a time through `shared/Widgets.qml`: opening closes the other listed widgets; `exclusive: false`, the clipboard, closes only the bar's menus and is never closed by others; a shell takes part by having the IPC target `widget` with `closeForOther()` (GlassPopup has it; no list to register in). `GlassSearchPopup.qml` (a `GlassPopup`) is the search field + list popup: `model`, `delegate` (a `GlassListRow`: click area, `selected`, `hovered`, hover plumbing, signal `activated()`), `placeholder`, `panelWidth/Height`, `emptyText`, signals `accepted(index)` (Enter) and `keyPressed(event)` (other keys), `searchText`, `list`. `app-launcher/Launcher.qml` and `clipboard/ClipboardPopup.qml` are now ~60 and ~110 lines on it; a new list popup is the same shape. Normal windows: `GlassWindow.qml` (a `FloatingWindow` with `shown`, `closeWindow()`, `focusItem` + `focusSoon()`, `hoveredItem`) and `GlassWindowPanel.qml` (first item of the content: the compositor glass, or the plain panel without it; `glassOn`), used by `SettingsWindow` and `WallpaperPicker`. Touchpad momentum for any list: `shared/KineticScroll.qml`. Not covered: `WallpaperOverlay` (own overlay, 1000 lines, not a `GlassPopup`). The paragraph below describes the state before this change.
`app-launcher/Launcher.qml` and `clipboard/ClipboardPopup.qml` are then only: the model, the panel `Rectangle` (transparent, with border) with the search `TextField` and `ListView`, the delegates setting `root.hoveredItem` in `onHoveredChanged`, `onPopupClosed` (clear search / reset selection) and the IPC handler.

Things learned the hard way (all verified, by screenshots with `grim` and logs):
- **Never toggle `visible` on these windows** (GlassPopup does not; use `shown`). Quickshell destroys and re-creates the Qt window, and with the glass items that segfaults (`QQuickWindow::maybeUpdate`, second show). The window stays mapped; a `shown` property drives `mask: shown ? null : emptyMask` (a `Region {}`), `WlrLayershell.keyboardFocus` (`Exclusive` while shown, `None` otherwise: `focusable` is only on-demand and often did not get the keyboard), `content.visible` and the backdrop's `active`. Focus is requested on show and again 60 ms later.
- **No translucent items over the glass, no shadow under it.** The background can only be recovered where the stack lets at least about 3% of it through; the glass is alpha 0.92 (8%). A translucent highlight on top (or a `RectangularShadow` under it) lowers that, and the sharp background then shows through there (or, with the shadow, because the shader cancels 8% where only 4% leaks). So the highlights (search field, selected row, hovered row) are drawn by the glass shader: `GlassPanel.hlRect0..2` / `hlColor0..2` / `hlRadius` (x, y, w, h in the panel's logical pixels, rgb + strength), set by GlassListPanel from the widgets' geometry with `mapToItem` (rows clipped to the list; the bindings list other values so they re-evaluate, since `mapToItem` is not tracked). Row and field backgrounds are `"transparent"`. `frost: 1.0` because the default 0.9 mixes 10% sharp background into the glass, which shows as faint text. (The status bar still uses 0.9.) Lowering the glass alpha is no cure: the shader's cancelling clamps at 0 over bright text.
- **Stale background on reopening: capture first, then show (implemented and deployed. Checked: launcher, scratch copy and deployed config. `present(true)` fired on every open, 12-44 ms after `shown` (44 ms on the first open, still in capture warm-up). Stale case, switching workspace between close and open in both directions (the other workspace shows different content; `grim` burst of the panel, RMSE of each frame against the steady state, with the previous deployed launcher as control): the control stays about 3% off the steady state for 0.2-0.5 s, with the sharp background text visible behind the panel; the new code shows no ghost from the first visible frame on. The cost: the popup appears about 50 ms later (median toggle to first changed pixel 147 ms against 98 ms for the old code, both including about 70 ms of IPC call; polling every 28 ms). NOT yet checked: the clipboard popup, the bar under load after the shader change, a bar that is not running), the clipboard, the bar after the shader change, load with the sweep scenario, deployment via `hms`).** The glass subtracts the leak of the background it saved last time; if the screen changed meanwhile, the old picture shows inverted. So `shown` only starts the capture: the content stays invisible (`presented` false), nothing of ours is in the frame, and the bar's tag shows at the tag's place. `unmix.frag` takes such a capture (`absentRed` = 30 matches the tag) as the background as it is, so the first update is fresh. `onFlipsChanged` then calls `present(true)`: content visible, `cancelAmount` 1 at once, no ramp (this runs inside `process()`, before the frame that shows it, so the frame also keeps the ring version the tag will name, content included). Cost: one capture round trip (about 2 frames) before the popup appears; to be measured. Fallback: if no update comes within `presentTimeout` (80 ms; screen unchanged, or no bar tag, e.g. the bar is not running), `present(false)` shows the content anyway, calls `GlassBackdrop.bumpVersion()` (the version the tag names must hold the content) and uses the old way: `cancelLeak` 0 until two updates (`revealTimeout` 400 ms), then ramped to 1 (`rampDuration` 150 ms; shorter ramps flashed, longer left the sharp background showing). Known gap: an update that comes from a rejected capture still counts as fresh (needs the bar's tag; if the bar is down the fallback is the likely path). Tried and rejected earlier: fade-in of the glass, hiding the popup until tagged captures arrive after showing (400 ms). Not tried: keeping the backdrop running while hidden (variant A, throttled standby; costs a capture stream per closed popup). Considered and rejected: one shared always-on blur for bar and popups (the bar's blur only covers its strip, each surface must unmix itself, the three shells are separate processes).
- **Drop shadow (launcher, clipboard and settings; not yet seen running):** `GlassShadow.qml` + `shaders/shadow.frag`, a child of `GlassListPanel` (`z: -1`, enabled with `shadow: true`), settings `Theme.popupShadowOpacity` (0 = off, default 0.3), `popupShadowBlur` (24), `popupShadowOffset` (8). The shader draws the shadow only outside the panel's rounded rectangle (nothing under the glass, which the rule above forbids); outside it the surface is otherwise empty, so the shadow's alpha (at most 0.3 by default) leaves 70% of the background, and the unmix removes it with the ring snapshot like everything else. The settings app has it too: its veil is 92% opaque, so a shadow over it leaves 0.08 x (1 - shadow alpha) of the background (5.6% at 0.3); `GlassShadow.maxOpacity` caps the opacity at 0.6 (3.2%, about the least that recovers). Unchecked: the veil with the shadow on it.
- Closing clears the search text, selection and scroll (so reopening starts clean).
- New files under `shared/glass/` must be `git add`ed before `hms`, like any new file. Both tags sit at the output's top left, over the bar's: while a popup is open the bar rejects its captures and keeps its last blur. The reds differ so that the bar's tag, which shows where a closed popup would be, is never taken for a version of the popup's.

Testing without touching the real config (no `hms` needed): copy the deployed config with `cp -rL ~/.config/quickshell/<name> <scratch>/dev`, edit it, run `qs -p <scratch>/dev` (kill the real instance first), and use `qs -p <scratch>/dev ipc call launcher toggle`. Shaders can be compiled by hand with `nix shell nixpkgs#qt6.qtshadertools -c qsb --qt6 -o out.frag.qsb in.frag`. `GlassPanel.debugMode: 1` shows the recovered background (magenta = unknown). Screenshots: `grim -g "x,y wxh" file.png` (logical coordinates; it takes about 100 ms per shot); `nix shell nixpkgs#imagemagick -c magick ...` to crop and stack them. Move the pointer with `hyprctl dispatch 'hl.dsp.cursor.move({ x = 720, y = 400 })'` (`hyprctl dispatch movecursor ...` does nothing here; this Hyprland uses a Lua config) and type with `wtype`. Caveat: a synthetic pointer move does not send motion to a surface that is already mapped, so the hover highlight only shows the row under the pointer at the moment the popup opened; move the pointer first, then open, to test hover (dynamic hover with a real mouse is untested).

**Launcher: overlay or window (`app-launcher/LauncherModes.qml`).** An app that can be opened two ways, as an overlay (its normal entry) or as a normal window, says so with a desktop ACTION whose id is `window` (`xdg.desktopEntries.<name>.actions.window` in `default.nix`; `quickshell-settings` (its action runs `qs -c settings ipc call settings toggleWindow`) and `quickshell-wallpapers` (the entry is the overlay, the action the window; see section 12)). The launcher shows an Overlay | Window pill on such rows (click it, or Tab on the selected row) and remembers the choice per desktop id in `~/.config/quickshell-launcher/modes.json` (`{"<id>": "window"}`, only "window" is stored; it honours `XDG_CONFIG_HOME`). Launching (click or Enter) goes through `LauncherModes.launch(app)`: the `window` action when set to Window, `app.execute()` otherwise. Other launchers just list "Open as window" as a normal desktop action. Checked in a scratch copy with test desktop entries (a test-only IPC hook set the search and called toggle/launch, since no clicks or keys can be sent safely): the pill only on the entry with the action, toggling writes and removes the file entry, overlay runs the entry's command and window the action's, a one-way app is unaffected. NOT checked: clicking the pill, the Tab key, the real settings entry in the launcher (needs `hms`), a new action appearing without restarting the launcher.

IPC and restarting:
- `qs -c app-launcher ipc call launcher toggle` (same form for `clipboard ipc call clipboard toggle`, `... call glass stats`). `launcher show` only prints the IPC listing here: use `toggle`/`hide`.
- Restart one instance: find its PID with `hyprctl layers | grep "namespace: app-launcher"` (the window stays mapped, so it is always listed; after a crash it is not) and `kill` it, then `(setsid qs -c app-launcher >/tmp/x.log 2>&1 &)`. A process can show up as `.quickshell-wrapped` and then `pkill -f "quickshell -c ..."` misses it. Beware that `pkill -f`/`pgrep -f` with a config name matches Claude Code's own shell command line and kills it (exit 144); use PIDs, or `pgrep -x quickshell` and read `/proc/<pid>/cmdline`.
- Clipboard: the instance also starts two `wl-paste --watch` processes (text and image). When replacing an instance, kill the old one and its children (`pkill -P <pid>`), or the watchers stack up.
- Crash reports: `~/.cache/quickshell/crashes/<id>/report.txt`.


## 11. The Lucent Hyprland plugin
The plugin is its own project now: **`~/Documents/Code/Lucent`** (source `src/main.cpp`, Nix `nix/`, test clients and analysis scripts `tools/`, and a `CLAUDE.md` there, gitignored, with how it works, the nested test recipe, all measurements and the pitfalls). Read that file before touching the plugin. What matters on this side:
- **What and why.** The old pipeline draws the glass at alpha 0.92 and subtracts an estimate of the 8% of the background that leaks through; the estimate is 35-90 ms old, so moving content behind a popup left a sharp ghost (the bar hid it behind its 10% sharp mix, `frost` 0.9). Lucent makes the captures a Quickshell process takes not contain that process's own layers (its own, plus other Quickshell processes' layers on the same or a higher layer level so that overlapping glass, e.g. the settings veil over the bar, cannot feed back into each other; grim/OBS/screen sharing untouched), so the capture is the background. It also rescues capture requests armed just after a commit they missed (otherwise 100-200 ms stalls). Hyprland 0.57.0 exactly; it refuses to load on a version mismatch, then Quickshell keeps estimating.
- **Which glass runs (since stage 4, `Theme.compositorGlass` is on by default).** Three ways, chosen by what is there, each falling back to the next: (1) the Lucent plugin offers `lucent_glass_v1` in version 3: the plugin draws the glass, nothing is captured, no lag; (2) the plugin is loaded but offers no (or an older) glass protocol, or the setting is off: captured glass in clean mode, one frame behind; (3) no plugin: captured glass with the estimating pipeline (sections 8 and 9). The shells switch between them while running, within about 3 s (the marker poll). Checked in a nested session with scratch copies of the four configs and an empty settings file: plugin loaded: all four on (1); plugin unloaded under them: all on (3), bar, launcher and settings look as before; loaded again: back on (1); shells started without a plugin: (3), and under a moving background the bar's estimating pipeline gives 60 updates and 60 window frames per second with nothing rejected (121 frames with `diagnostics` on: the counting pass costs a frame per update, which is only for measuring). An output with a transform gets no glass from the plugin (it draws none there, and the shell cannot tell): turn the setting off for such a monitor.
- **Compositor glass (branch `feature/compositor-glass` in both repos; stages 1 to 3: the status bar, the launcher, the clipboard and the settings, with the whole look).** Captured glass is one frame late at best; here the plugin draws the glass itself while Hyprland makes the frame, so there is no lag (how: Lucent's CLAUDE.md, section 3b). Protocol `lucent_glass_v1`: `shared/glass/native/lucent-glass-v1.xml` is a COPY of Lucent's `protocol/lucent-glass-v1.xml` (keep them the same; the native module generates its client code from it). `Glass.Native` has `LucentGlass` (`native/lucentglass.cpp`): an item whose area is the glass; `available` (the plugin offers the global in version 2 or later), `active`, `blurRadius`, `maxTaps`, and the look with the names and meaning of `GlassPanel` / `GlassStyle` (`frost`, `bevel`, `edges`, `tint`, ..., `hlRect0..2`, `holeRect`). `shared/glass/LucentGlassPanel.qml` binds those to a `GlassStyle`: it is the drop-in counterpart of `GlassPanel` (the plugin runs a port of `glass.frag`). Qt lowers a client extension's version to what a global offered and never raises it: `LucentGlassManager` asks for its own version again when the global goes, or a shell that saw an old plugin build would never use a new one. It sends its state in `updatePolish()` and asks for a frame, so the compositor applies it with that frame's commit. When the global goes away (plugin unloaded) the object is dropped WITHOUT a request (a request on it would be a protocol error and end the shell). `Theme.compositorGlass` (Settings > Glass, on by default since stage 4, applies live): `StatusBar.qml` then uses a `LucentGlassPanel` with the bar's `GlassStyle` instead of the `GlassPanel`, and `glassEnabled` of the bar's `GlassBackdrop` goes off (no capture). Without the plugin, or with a build that has no glass, the bar keeps the captured glass. Checked in a nested Hyprland with a scratch copy of the bar's config: the look, switching the setting both ways live, lag -0.6 ms with the moving bar (captured glass: one frame), cost about a third. Loaded into the live session (system rebuild, `hms`, `qsr` swapped the plugin without trouble) and checked on the real bar through the settings file: lag -0.7 ms with the moving bar (stdev 1.8); over the moving test background Hyprland 11.1% CPU / 40.6% GPU and the bar 0.1% / 0, against 16.5 / 51.8 and 15.2 / 2.9 with the captured glass; switching back restores the captured glass. Stage 2 (the look), nested and then live (rebuild, `hms`, `qsr` on 2026-11-16; on the real bar lag -0.4 ms, Hyprland 11.4% CPU / 42.5% GPU and nothing in the bar over the moving test background): the plugin's glass against the captured `GlassPanel` on the same popup-like panel RMSE 0.0011 (0.015 on the bar, where the captured glass only blurs its own strip); lag -0.5 ms; old shell with new plugin and new shell with old plugin both work (the latter on captured glass). **Stage 3 (popups and settings):** `GlassPopup.compositorGlass` (asked for and offered; it has a `LucentGlass` only to ask `available`) turns the popup's capture off and shows the content at once (nothing to wait for: the glass is of the frame it appears in). `GlassListPanel` is now an `Item` holding the shadow, the captured `GlassPanel` and a `LucentGlassPanel` with the same style and highlights, one of them shown (the `GlassPanel` inside it needs `originPx` from the wrapper: its own x and y are 0 now; forgetting that showed a shifted picture in the panel). `GlassScrim` has a `LucentGlassPanel` for the veil (the plain veil below 3 px of blur is unchanged); the plugin blurs once for veil and panel. Regions are sent with fractions (protocol version 3, which `available` now needs). Also fixed on the way: a capture that is turned on again publishes its first picture even if the screen looks as it did at the last one (`GlassCapture::setActive`, `mForcePublish`); before, switching back to captured glass over a still desktop left the bar a plain tint until something changed, and a popup opened over an unchanged screen waited for `presentTimeout`. Nested: launcher, clipboard and settings against their captured glass RMSE 0.004 / 0.008 / 0.005 (whole screen); lag in the launcher -0.3 ms; cost with a moving background, launcher open 7.2% CPU / 34.0% GPU in all against 31.8 / 63.2, settings 7.4 / 40.1 against 36.9 / 64.7. One difference in what is blurred: the plugin blurs everything that is really below, other Quickshell surfaces on the same layer level included, which the captures leave out. Live since 2026-11-16 (the user rebuilt and ran `qsr`): all four shells on the plugin's glass, lag in the launcher's panel -0.8 ms, launcher, clipboard and settings (veil at radius 4) look right in screenshots, no crash reports. NOT checked from here: mouse hover on rows with the plugin's glass (no way to move a real pointer).
- **Glass behind windows (protocol v4, written 2026-11-17, nothing deployed).** The plugin also draws the glass behind the toplevel surface of a normal window (a Quickshell `FloatingWindow`; how: Lucent's CLAUDE.md, section 3b), and switches Hyprland's own blur off for such a window while it has glass (no `no_blur` rule needed). `LucentGlass` asks for version 4 and `available` needs 3 on a layer surface and 4 on a toplevel (a plugin that offers 3 draws nothing behind windows: `available` is false there, so use a fallback such as a plain tinted panel). The kind of surface is read from the `QWaylandWindow`'s shell surface (`QWaylandXdgSurface` = toplevel; a type with "Layer" in its name = layer shell); it is only known once the window exists, so `available` is re-read (and `availableChanged` sent) when the window shows. A window has no platform surface until it is visible: `LucentGlass` connects `QWindow::visibleChanged` to `polish()`, or a `FloatingWindow`'s glass was never made. Use a test build of the module with the PLAIN `quickshell` package's `qs` (the profile's `qs` wrapper prepends the deployed `Glass.Native` and ignores yours). Nested test with a scratch `FloatingWindow` + `LucentGlass`: glass inside the client's frame, lag 0 frames, move/resize/slide/fade/fullscreen fine. **Protocol v5:** `LucentGlass.bevelProfile` (also `GlassStyle.bevelProfile`, default 3, bound in `LucentGlassPanel.qml`) sets the curve of the rim, (1 - u^n)^(1/n): 2 is the old quarter circle (the bending ends in a visible edge where the rim meets the flat middle), 3 fades it out, 4 more so; it is only sent to a plugin that offers version 5, and the captured `GlassPanel` always has n = 2. The picker conversion itself (`wallpapers/`, branch `feature/wallpaper-picker`) is NOT done.
- **Consumer side (this repo).** `shared/LucentStatus.qml` reads the marker `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/lucent-active` (section 8, "Clean mode"). `hyprland.lua` loads `/etc/hypr/plugins/liblucent.so`. It was called `pane` until the rename (`libpane.so`, marker `pane-active`); the consumer only knows the new marker now, and the plugin still refuses to load while an old build's marker exists.
