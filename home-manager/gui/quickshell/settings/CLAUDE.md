# CLAUDE.md — settings app and Theme overrides (moved from the root CLAUDE.md; original section 10)

## 10. Theme overrides and the settings app
**Overrides.** `Theme.x` = `ThemeDefaults.x` unless the settings app set it. Overrides live in `~/.config/quickshell-settings/settings-app-theme.json` (outside the store, survives `hms`; flat JSON with only the changed keys, named like the `ThemeDefaults` properties), read by the `ThemeFromSettingsApp` singleton (`FileView`, `watchChanges`), so all shell processes update live. Invalid keys or JSON fall back to the defaults. Verified (scratch config with `XDG_CONFIG_HOME` pointed at a scratch dir, and in the real shells): edit and atomic replace of an existing file are picked up; a file that does not exist at start is picked up through a 2 s retry timer (Quickshell cannot watch a missing file); the first value is correct within about 1 ms of start; a write from the settings app changed the real bar's border within a second. Adding a theme value: a line in `ThemeDefaults.qml`, one in `Theme.qml` with the same name, and an entry in `settings/ThemeSchema.qml` (the page and the search both read the schema; `ThemePage.qml` has no per-value code).qml`. Bar and glass values that were hardcoded come from `Theme` (`barBorderColor`, `barBorderOpacity`, `barFillOpacity`, `glassBlurRadius`, `GlassStyle.tint`, the `AudioMenu` colours).

**Hyprland category: window rules with glass parameters (2026-11-17).** A second category in the settings app (`SettingsIndex.categories`, page `HyprlandPage.qml` in `SettingsView`'s `StackLayout`; it has no searchable settings: `sections: []`). Files: `HyprlandStore.qml` (singleton: the rules, validation, the Lua generator and parser, writing, reload, the base-config parser), `HyprlandPage.qml`, `RuleCard.qml` (one rule: header with enable switch, duplicate, delete; editor: name, match, glass), `ParamRow.qml` (a glass parameter: slider or colour, ↺ when set), `TextRow.qml`, `Segmented.qml`. **Where it writes:** `~/src/nix-config/home-manager/gui/hyprland/hyprland-settings.lua` (next to the source of `hyprland.lua`, like hyprmod's `hyprland-gui.lua`; env `HYPRLAND_SETTINGS_FILE` overrides it for tests). It is in `.gitignore` (`home-manager/gui/hyprland/hyprland-settings.lua`; note the older entry for `hyprland-gui.lua` points at a path that does not exist, so that file is tracked) and `hyprland.lua` `dofile`s it **at its very end**, so its rules come after the base config's. **No hms:** after a change (600 ms pause) the store writes the file and runs `hyprctl reload`, then reads `hyprctl configerrors` 800 ms later and shows the lines about this file (line number and message; `hyprctl reload` failing shows its error). **Checked in a headless nested Hyprland** (`AQ_BACKENDS=headless` still opened a small window on the host; start with `env -u HYPRLAND_INSTANCE_SIGNATURE`, kill the real `Hyprland` child by PID with `kill -9`, the PID file only holds the wrapper): a later rule overrides an earlier one for the same effect (both ways); `hyprctl reload` re-reads the file, re-applies rules to windows that are ALREADY OPEN (checked with a `tag` effect) and drops removed rules; `configerrors` reports unknown fields, wrong value types and syntax errors with file and line, but NOT an invalid regex or a bad `lucent_glass` string (the app validates regexes with JS `RegExp` and `tint` itself, and does not write such a rule); the Lua API has no way to list rules (no getter in `share/hypr/stubs/hl.meta.lua`), so the base config's rules are parsed from the text of `~/.config/hypr/hyprland.lua` (comments stripped, `hl.window_rule({...})` tables read; `lucent_glass` given as strings or `table.concat` is read back into parameters), only to list them read-only and to start an **Override** (a new rule with the same match and glass). The whole chain with the real plugin in the nested session: adding a glass rule from the app turned an open translucent window from Hyprland's blur to the plugin's tinted glass (stripe contrast 0.26 to 0.003), "Glass off" brought the blur back, disable/enable/delete applied live, and the app read its rules back from the file after a restart. **The data model:** a rule is `{id, name, enabled, match: {class, title, initial_class, initial_title, float: ""|"yes"|"no"}, glass: {mode: "inherit"|"custom"|"off", params}}`; the file holds the rules as Lua (`hl.window_rule({name, match, lucent_glass = "radius=14 tint=... "})`, inside `if io.open("/etc/hypr/plugins/liblucent.so")` because `lucent_glass` is unknown, an error, without the plugin) and, in a `--[====[ quickshell-settings ... ]====]` comment, the same rules as JSON, which is what the app reads (do not edit the file by hand). "No change" (inherit) and rules with nothing to match, a bad regex or a bad tint are not written (the card says why); "Glass off" writes `lucent_glass = "false"`, which switches the glass of a base rule off for those windows; custom writes only the parameters that were changed (the rest keep the plugin's defaults, shown dimmed; no parameter = `"true"`, a plain blur). The first rule of the list is written LAST, so the rule higher in the list wins when several match one window. The 17 parameters and their ranges are in `HyprlandStore.glassParams` (from Lucent's README table; the sliders use smaller ranges for some). Not covered on purpose (for now): other effects (float, size, opacity, ...), other kinds of rules, Hyprland options. NOT checked: clicking and typing in the page (all changes went through a test-only IPC hook that was not kept; the screenshots show the page), a first run on the live session (nothing here was run against the live Hyprland: the scratch app's reload target was a nested instance or a bogus signature), the `dofile` line in the deployed `hyprland.lua` (needs `hms`; the same lines were used in the nested config), the settings window form of the page, regexes that JS accepts and RE2 rejects (or the reverse).

**Glass settings and collapsible groups (2026-11-17).** The Glass section of the schema (`ThemeSchema.qml`) keeps three settings visible (Live glass, Compositor glass, Blur radius) and has `groups`: collapsible sub-sections `{ id, title, note, items }` (a section may have them next to its `items`; only Glass does). `ThemePage.qml` shows each as a header row (chevron, title, note) that opens on click, all closed at start (state in `openGroups`, in memory only); a closed group shows an accent "n changed" badge when some of its settings differ from the defaults, so a change cannot hide in it. `scrollTo(key)` (the search's jump button) opens the group of that setting first, waits 60 ms for the layout, then scrolls. `SettingsIndex` indexes the grouped settings too (their place is "Glass › <group>", so a group title is searchable and shows in the result's note). The groups: **Panels** (opacity + the look), **Status bar** (the bar's look), **Popup shadow**, **Settings desktop blur** (`scrimBlurRadius`), **Blur performance** (`blurMaxTaps`, `blurTapsFalloff`). The old Popups section is gone (merged in); `backdropBlur` ("Legacy blur, unused") is no longer listed (the Theme value and the legacy `BackdropBlur.qml` are still there). **The look settings** are the parameters of `GlassStyle` / the Lucent plugin's glass, twice: `glassPanel*` for the panels (launcher, clipboard, settings, wallpaper picker) and `glassBar*` for the status bar: Frost, Tint (`TintStrength`), Brightness, Contrast, Saturation, Rim width (`Bevel`), Rim height (`Thickness`), Rim curve (`BevelProfile`, compositor glass only), Refraction, Index of refraction (`Ior`), Dispersion, Shine. Their defaults are exactly the looks the shells had before (panel: frost 1, tint 0.65; bar: frost 0.9, tint 0.35; the rest the same). They reach the glass through `shared/glass/PanelGlassStyle.qml` and `BarGlassStyle.qml` (a `GlassStyle` bound to `Theme`), used by `GlassListPanel` (popups, settings overlay: its extra tint at a low blur radius is added on top, capped at 1), `LucentListPanel` (windows: the settings window and the wallpaper picker) and `StatusBar.qml`; they apply live, both for the compositor glass and the captured glass (except the rim curve). Not settings (still fixed per element): corner radius, which edges have a rim, the tint colour (= `Theme.background`), the veil's tint, the light direction, and `GlassStyle.alpha` / `opacity`. The Lucent window rule keys for other programs' windows (the kitty rule in `hyprland.lua`) are NOT connected to these settings. Checked (scratch copy of the deployed settings config with the working tree's settings and shared QML, `qs -p`, with a test-only IPC hook that was not kept: it opened groups, called the jump scroll and ran `SettingsIndex.search`): the collapsed section, a jump into a closed group (opens, scrolls, outlines the row), the open Panels group, the "5 changed" badge, search finding grouped settings, and that overrides in the scratch settings file (tint 0.1, rim width 34, refraction 3, thickness 1.6, dispersion 0.3) visibly changed the settings overlay's glass (clearer, wide rim, colour fringe). All five configs build with `nix build`. NOT checked: clicking a group header (no clicks possible), the new values on the bar, launcher, clipboard and the wallpaper/settings windows in real use (the same code path as the settings overlay), the captured-glass fallback with them, whether extreme values look good, and the settings window's version of the page.

**Settings app** (`settings/`, config `qs -c settings`). **Two forms, one content** (added 2026-11-17, branch `feature/wallpaper-picker`): the full-screen OVERLAY (`Settings.qml`: a `GlassPopup` with the veil and a `GlassListPanel`, as described below; namespace `settings`, tag red 34 like the launcher, so do not open it together with the launcher) and a NORMAL WINDOW (`SettingsWindow.qml`: a `FloatingWindow` titled `Settings`, tiled by Hyprland like any window, with compositor glass through `LucentListPanel`, see `shared/glass/GLASS-WINDOWS.md`; no veil, no captured glass, no shadow of its own; opaque panel without the plugin; created in a `Loader` only while open, so it starts fresh; Super+C closes it like any window). What is inside (sidebar, search, pages, keys) is `SettingsView.qml`, used by both hosts (`glassOn` false = plain fills for the highlights; it asks the host to close with `closeRequested()`). The IPC target `settings` is in `shell.qml`: `toggle`/`show` = overlay, `toggleWindow`/`showWindow` = window, `hide` = both, `isOpen` = the OVERLAY only (the Super+C bind uses it; a window is closed by the compositor like any other). Opening one closes the other. The bar's gear button still opens the overlay. In the app launcher the user chooses which one an app row opens (section 9, "Launcher: overlay or window"). Checked (scratch copy of the deployed settings config, live session): the window (tiled, glass, same pages, category highlight), the overlay (veil, highlights, unchanged look), switching between them through IPC, `hide`, no crash report. NOT checked: keys, mouse and search in the window form (the content is the same code as the overlay's, but nothing was typed), a floating or resized window, Super+C on the window, a long run.
Files: `Settings.qml` (overlay host), `SettingsWindow.qml` (window host), `SettingsView.qml` (the content: sidebar, keys: Esc / Ctrl+C close, Up/Down categories), `ThemePage.qml` (the schema: sections and items; one entry per `Theme` value), `ColorField` (swatch, hex field, picker), `NumberField` (stepper for ints, slider for reals), `SwitchField`, `SettingsRow` (label, note, reset arrow), `ThemeStore.qml` (singleton that edits and writes). Store: `preview(key, v)` changes the value in this process only (drags), `commit()` writes (30 ms coalesced), `set` = both; a value equal to its default is removed from the file; `ThemeFromSettingsApp.ownWrites` makes the loader ignore reads of the app's own recent writes (a late file-watcher reload used to overwrite newer in-memory changes). Controls are opaque or outline-only (no translucent items over the glass, section 9). Opened by the bar's gear button (`status-bar/SettingsButton.qml`, runs `qs -c settings ipc call settings toggle`); started at login by `hyprland.lua` (`hl.exec_cmd("qs -c settings")`, needs a Hyprland restart or a manual start the first time) and by `reload.sh`.
Super+C: Hyprland swallows it (the app is a layer surface, not a window), so the bind in `hyprland.lua` asks `qs -c settings ipc call settings isOpen` and hides the app if it is open, else closes the focused window. Turning `Theme.glass` off at runtime: `GlassPanel.known` is `backdrop.ready && backdrop.glassEnabled` and `GlassBackdrop` clears `ready` when the glass goes off, so the panel becomes the plain tinted one at once (checked live with the file) and comes back with a fresh blur when it is turned on again; before this the last blur stayed on screen.
**Veil over the desktop (scratch-tested, then deployed):** while the settings are open the whole desktop is blurred (`shared/glass/GlassScrim.qml`), so that it is clear that only the settings can be used and that a click elsewhere closes them (the full-screen `MouseArea` under the panel does that; the veil takes no mouse). It is one full-surface `GlassPanel` (no bevel, `frost` 1, tint strength 0.3) with a rounded hole cut out where the settings panel is: `GlassPanel.holeRect` / `holeRadius`, done in `glass.frag` (`coverage *= ...`; the hole follows the panel's rounded corners; an earlier version of four rectangular pieces left a speck of sharp background in each corner notch). It is not a second panel under the settings panel: two glass layers over each other leave under 3% of the background, which cannot be recovered. The panel's edges are on whole *physical* pixels (`GlassGeometry.alignedSize`, `round(v * ratio) / ratio`, so the panel is 621 px tall at scale 1.333). `GlassTag` has `z: 1000` in `GlassPopup` so that the veil never covers the tag pixel. The settings window's `blurRadius` is `Theme.scrimBlurRadius` (default 10.5, a setting in the Glass section; checked live at 2 / 10.5 / 30 through the file; one blurred picture serves veil and panel; at about 8.4 faint text from the windows behind showed through the panel, at 14 the desktop was judged too blurred). Radius 0 and glass off (checked in scratch): the blur pass always leaves a little softness even at sigma 0, so `GlassScrim` mixes in the sharp picture below a radius of 3 (frost = radius / 3); but the glass cannot show the desktop sharp: the veil is 92% opaque, so recovering the picture divides the screenshot by 0.08, which multiplies its 8-bit rounding by about 12 and turns smooth gradients into flat steps about 12 levels apart (measured on the status bar's blurred edge: a smooth ramp 203 to 174 became 175 / 164 / 154; the bar itself was unchanged, checked with the veil cut away over it), and only a blur hides that. So below `plainBelow` (3 px) the veil is not glass but a plain 35% tint (`Shape` with the panel's rounded rectangle as an odd-even hole, `Shape.CurveRenderer`), and the desktop shows exactly as it is (checked: bar profile smooth, corners clean, no visible steps at 2.9 and 3.1); the settings panel's tint grows as the radius falls (0.65 from 8 px of blur up, about 0.95 at 0; `GlassListPanel.tintStrength`) so that sharp text behind it does not show through; with the glass off the veil is the same plain tint (the `GlassPanel` would draw an opaque tint and hide the desktop). Not checked: a click outside (no way to click from here), cost of a full-screen glass while open, multi-monitor.
**Blur radius applies live:** a `GlassBundle`'s blur passes are not live (`scheduleUpdate`), they were rendered only when a capture arrived (`process()`), so a new `Theme.glassBlurRadius` showed on the status bar only when the screen behind it changed (an idle bar: not until the next capture). `GlassBackdrop.onBlurRadiusChanged` now calls `GlassBundle.reblur()` on the shown bundle (the two blur passes from the settled background; deferred with `Qt.callLater` so the bundle's sigma has updated). Reproduced and fixed in a scratch copy with captures stopped (`qs -p ... ipc call glass setCapture false`): before, radius 40 to 2 changed the picture by 0.015 (RMSE, normalised), after a resumed capture by 0.069; after the fix 0.072 at once, and back to 40 gave the original picture again. Not run on the real status bar (it would need its settings file changed).
**Section buttons:** a section in `ThemeSchema` can have `button: "<id>"`, an action of `ThemePage.actions`; the Status bar section has `restartBar` (a row at the end of the section with the button where the controls are): it kills the bar process found from `hyprctl layers` (`namespace: statusbar`; not `pkill -f`, which would match the command itself) and starts `setsid -f qs -c status-bar` after 0.6 s; it shows `Restarting…` for 3 s. If the bar is not running it just starts it. Expected, not checked: a bar restarted while the settings are open has no glass until they are closed (the settings' tag is over the bar's, section 9). Checked in a scratch copy: the button renders; the PID that `hyprctl layers` gives is the bar's process. NOT run end to end (it restarts the real bar).
**Trackpad momentum:** `settings/KineticFlickable.qml` (a `Flickable`, used by `ThemePage`) takes the wheel events that carry a `pixelDelta` (two-finger touchpad scrolling; a mouse wheel has none and is left to the Flickable) with a `MouseArea` (`acceptedButtons: NoButton`), moves the content itself, and when no event has come for 60 ms (fingers up) glides on with the speed of the last ~100 ms (`glideTime` 0.35 s time constant, no glide below 150 px/s, max 8000 px/s); a new touch event or a drag stops it, the page ends stop it. Qt on Wayland gives no momentum, so it is done here. Checked with scripted events in a scratch copy (flick: glide distance about speed x 0.35 s with smooth decay; new touch stops it; slow scroll does not glide; flick past the top stops at 0). NOT checked with a real trackpad (no way to produce those events from here): whether the touchpad's events really arrive with a `pixelDelta` and reach the `MouseArea`, the feel (`glideTime`, `minGlideSpeed`), and whether the direction is right.
**Search** (deployed; only partly tested, see below). The settings definitions are in `settings/ThemeSchema.qml` (sections, items, `keywords` = synonyms); `SettingsIndex.qml` holds the categories and the search: all words must match, score = label (prefix 100, word start 80, substring 60) > synonyms (50/40) > property name (35/30) > section/category (25) > note (20), ties in page order. `SettingField.qml` picks the control by type (used by `ThemePage` and `SearchResults`). `Settings.qml`: a `TextField` above the page (it is the `GlassListPanel`'s `field`, highlight drawn by the glass); results replace the page while the query is not empty (the page stays alive). Results are grouped by category, the selected one first (`In Theme`), with the real controls (edit in place) and a jump button (`jumpTo`: selects the category, clears the search, `ThemePage.scrollTo(key)` scrolls and outlines the row for 1.4 s). `Only in <category>` chip (Tab) limits to the selected category; it shows only with more than one category. Sidebar rows show match counts while searching. Type-to-search: `Keys.onPressed` of the `keys` FocusScope only sees keys the focused item did not use; a text field uses all printable keys, so typing a value never searches; with nothing like that focused, a printable key (no Ctrl/Meta; AltGr allowed; not a leading space) goes into the search field. Esc: clears the search first, then closes. The empty search field shows only a magnifier icon (the hint "Search settings…" and the cursor only while it has focus). The field gives up focus on Esc, when the popup closes, and when the panel is clicked anywhere else while the field is empty (with a search going on it keeps the focus); choosing another category (click or Up/Down) clears the search and the `Only in` chip. The click part is a `MouseArea` (z 10000, over the whole panel) in `Settings.qml` looks at every press and sets `mouse.accepted = false`, so the press goes on to what is under it (a `TapHandler` on a parent, or on an overlay, did not work: scrolling lists took the press first, and a passive `TapHandler` overlay stopped the search field from getting its own click). Checked with synthetic clicks (`import QtTest`, `TestCase.mouseClick` in a scratch copy: a test hook that is not in the repo). Up/Down still switch category (which changes the group order). Adding a category: an entry in `SettingsIndex.categories` and a page in `SettingsView.qml`'s `StackLayout`. Tested in a scratch copy with `wtype`: type-to-search, results and counts, Esc twice, synonyms. Also tested in a scratch copy with a made-up second category (not in the repo): the grouping (`In Theme` first, then `In Other`), the `Only in` chip and Tab, match counts, and that choosing another category by click or Up/Down clears the search and the chip. Confirmed by the user on the deployed app: the jump button works, and typing in a hex value field does not start a search. Still not tested here: nothing known.
Checked with a scratch copy (screenshots of the open window, the store through a test IPC hook): layout of all sections, the open picker, writes, reset, cross-process update of the real bar. NOT checked: mouse interaction with the controls (no way to click from here), keyboard in the hex field, hover highlight on the sidebar, whether `Theme.glass` and size changes apply live (the page says "may need a restart").
