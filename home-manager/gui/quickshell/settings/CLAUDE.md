# CLAUDE.md — settings app and Theme overrides (moved from the root CLAUDE.md; original section 10)

## 10. Theme overrides and the settings app
**Overrides.** `Theme.x` = `ThemeDefaults.x` unless the settings app set it. Overrides live in `~/.config/quickshell-settings/settings-app-theme.json` (outside the store, survives `hms`; JSON with only the changed keys, named like the `ThemeDefaults` properties, the groups nested: `{"glassBar": {"tintStrength": 0.45}}`), read by the `ThemeFromSettingsApp` singleton (`FileView`, `watchChanges`), so all shell processes update live. Invalid keys or JSON fall back to the defaults. Verified (scratch config with `XDG_CONFIG_HOME` pointed at a scratch dir, and in the real shells): edit and atomic replace of an existing file are picked up; a file that does not exist at start is picked up through a 2 s retry timer (Quickshell cannot watch a missing file); the first value is correct within about 1 ms of start; a write from the settings app changed the real bar's border within a second. Adding a theme value: a line in `ThemeDefaults.qml`, one in `Theme.qml` with the same name, and an entry in `settings/ThemeSchema.qml` (the page and the search both read the schema; `ThemePage.qml` has no per-value code). Bar and glass values that were hardcoded come from `Theme` (`barBorderColor`, `barBorderOpacity`, `barFillOpacity`, `glassBlurRadius`, `GlassStyle.tint`, the `AudioMenu` colours).

**Undo / redo (2026-11-20).** `settings/SettingsHistory.qml` is one snapshot-based stack for the whole app: Ctrl+Z, Ctrl+Shift+Z / Ctrl+Y in `SettingsView` (both hosts) and Undo / Redo buttons at the sidebar bottom. A step = one `commit()` of a store (commits of one store within 600 ms merge: typing, slider bursts; a drag is one step because `preview()` does not commit). **A new store takes part by**: `SettingsHistory.register(store, () => state, s => { put state back; commit() })` once, `SettingsHistory.committed(store)` at the start of its `commit()`, and `SettingsHistory.rebase(store)` when state is read from outside (file load, migration). Settings, pages and controls need nothing. `ThemeStore` (the values) and `HyprlandStore` (`{rules, follow}`) are registered. **Showing what changed:** a store can pass a fourth argument to `register`, `locate(from, to) -> { catId, key } | null`; after an undo or redo `SettingsHistory.revealRequested` makes `SettingsView.jumpTo(catId, key, gentle=true)` switch to the page and call the page's `scrollTo(key, gentle)`, which opens what has to be opened and outlines the row (`FlashFrame`, an accent outline for 1.4 s, not faded: nothing translucent over the glass); `gentle` scrolls only if the row is not completely in view (`SettingsPage.show`). Theme: the first changed setting in schema order (`ThemeStore.locate`; `ThemePage.scrollTo` already opens collapsed groups and own-look widgets). Window rules: a rule id, `<id>#<field>` (`name`, `match.<k>`, `effect.<i>`, `param.<k>`: a row with `fieldId`, found by `RuleCard.find`) or `base:<name>` (`HyprlandStore.locate`; the enable switch and the glass mode outline the whole card). A new page with its own state implements `scrollTo(key, gentle)` the same way. NOT checked at runtime: only lint and build.

**Page structure (2026-11-20, branch `feature/settings-reorg`; replaces the one long "Theme" page).** The sidebar has top-level groups (`SettingsIndex.groups`: Theme, Hyprland; a heading each) and under them the categories, one page each: Theme › Appearance, Status bar, Panels, Notifications, Glass (each a `ThemePage { catId }`, defined in `ThemeSchema.categories` with `group: "theme"`), Hyprland › Window rules (`HyprlandPage`, id `windowRules`, added in `SettingsIndex.categories`). The categories are one flat list in sidebar order; the pages in `SettingsView`'s `StackLayout` must be in the same order. To add a top-level group: an entry in `groups`, categories with that `group`, their pages. The sidebar is still the `categoryList` ListView (the glass highlight reads its `currentItem`), with a `ListModel` (roles `catId`, `name`, `icon`, `groupName`, filled from the categories at start) so that ListView `section`s can draw the headings (`BlockTitle`); the headings are not rows. Where things are: the panels' glass look, opacity, shadow and the settings backdrop blur on Panels; the bar's glass look (section "Glass") on Status bar; Glass has only the switches, blur radius and Performance. A category has `name`, `icon`, `description`, `actions` (ThemeActions ids: `restartBar`, `testNotification`) and `sections`; a section has a `kind`: `list` (items, then titled `blocks`), `colors` (`ColorGrid`: swatch cells, the full `ColorField` with picker opens under the block of `ThemeStore.openColor`), `table` (`SizeTable`: rows x columns of `Stepper`s, one reset arrow per row), `collapsed` (`ThemeGroup`; Glass › Performance). (A `tabs` kind existed briefly; the user found the tabs not recognisable as tabs, so the looks were split by page instead.) An item can have `showIf: { key, is }` (Clock and Indicator style only with the Balanced layout). `ThemeSchema.flatten(section)` lists the settings with their block; `SettingsIndex` indexes them (place "Panels › Glass › Rim"; a word matching the group, category, section or block name finds all under it; result groups are titled "In Theme › Panels") and gives `keysOf(catId)` (the sidebar's accent dot for a page with changes, "Reset page" = `ThemeStore.resetKeys`). `ThemePage.scrollTo(key)` opens a collapsed section, or for a hidden `showIf` setting goes to the setting it depends on. Every page has a `PageHeader` (title, description, buttons: the actions, "Reset page"; Window rules: "+ Add rule", "Reload Hyprland"); "Reset all to defaults" is at the bottom of the sidebar. Rows (`SettingsRow`): the controls take a column of `min(340, width * 0.55)` (sliders fill it, the others sit at its right), notes wrap up to three lines and the row grows. `Segmented` with `stretch` (the choice rows) makes all segments equally wide (the widest label measured bold, so choosing one does not change sizes, or an equal share of the column, whichever is more; uneven segments were reported). `SectionAction` became `ActionButton` (a plain button). Checked in a scratch copy of the deployed config with the working tree's settings QML (`qs -p`, a test-only IPC hook to switch pages, scroll, jump and search, not kept): all six pages, the headings and the highlight, Down across the heading (`wtype`), the open colour editor, jumps to the bar's glass (Status bar), Panels › Shadow and into the closed Performance section, search across groups. NOT checked: clicking (cells, header buttons, choices), the window form, the bar's restart from the header.

**Grouped Theme values (2026-11-20, branch `feature/nested-theme`).** The glass looks and the shadows are objects in `Theme`: `Theme.glassDefault` and the widgets' looks are `shared/GlassLook.qml` (frost, tint, tintStrength, brightness, contrast, saturation, bevel, thickness, bevelProfile, refraction, ior, dispersion, shine), `Theme.popupShadow` / `notificationShadow` are `shared/ShadowLook.qml` (opacity, blur, offset); their defaults are plain objects in `ThemeDefaults` (`ThemeDefaults.glassBar.frost`). In the settings file they are nested objects (`{"glassBar": {"tintStrength": 0.45}}`); in memory (`ThemeFromSettingsApp.values`) a grouped key is a path, `"glassBar.tintStrength"` (`flatten` on read, `nest` in `writeValues`, which `ThemeStore` writes with), and the schema's `key` is that path, the settings app reads values with `Theme.value(key)` and defaults with `ThemeStore.defaultOf(key)` (never `Theme[key]`). Adding a look parameter: a line in `GlassLook.qml`, a value in each of the three looks in `ThemeDefaults`, an entry in `ThemeSchema.lookBlocks`. **Old flat keys** (`glassBarTintStrength`, `popupShadowOpacity`, ...) are rewritten once to the groups by `ThemeStore.migrate()` (when the settings app loads the file; values equal to the default are dropped; only the settings app writes the file). Checked in a scratch copy with an old-style file: the migration (written nested, read back after a restart, a later change added to its group), the values through `Theme` (looks in use, shadows, the window rules' default look), jumps to nested keys, search, no warnings. NOT checked: the bar, popups and notifications running with the new Theme (same bindings, lint only).

**Per-widget glass looks (2026-11-20, branch `feature/widget-glass`; replaces `glassPanel`, `glassPanelLook` / `glassBarLook`, `PanelGlassStyle` / `BarGlassStyle` and `Theme.panelGlass` / `barGlass` of the paragraph below).** Every widget has a `GlassLook` in `Theme` with `base: glassDefault`: `glassBar` (the bar and its small pills; own by default, as before), `glassBarPanels` (the bar's "strong" pills: Wi-Fi, volume, power panels, notification centre, the indicator), `glassLauncher`, `glassClipboard`, `glassSettings` (overlay and window), `glassWallpapers` (the picker window), `glassNotifications` (the cards), `glassWallpaperOverlay` (Super+W: only its blur is used, behind the side pictures, `WallpaperOverlay.sideBlur`; own by default with blur 7, the old value; its widget entry shows only the Blur block: `widget(..., only)`). Every look has a **blur radius** (`GlassLook.blurRadius`, a Blur block first in each look; the default look's is the setting `glassBlurRadius`, moved there from General; widgets use `<name>.blurRadius`), used by `GlassSearchPopup` (GlassPopup's `blurRadius`), `Settings.qml`, `GlassWindowPanel`, `NotificationCard`, `BarPill`, `StatusBar`'s backdrop and the overlay. `ThemeDefaults` holds only what differs from the default look (`glassBar: { look: "own", frost: 0.9, tintStrength: 0.35 }`, the others `{ look: "default" }`). A look's `look` ("default" / "own", key `<name>.look`) picks `inUse` (itself or the default look); a value its own look does not set is the default look's, LIVE (`GlassLook.fallback`), so an own look stores only what was changed, and `ThemeStore.defaultOf` asks the look (`GlassLook.defaultOf`) so that a value set back to the default look's is dropped from the file. Widgets draw with `ThemedGlassStyle { look: Theme.glassX.inUse }`; `GlassListPanel`, `LucentListPanel`, `GlassWindowPanel`, `GlassSearchPopup` take a `look` (default `Theme.glassDefault`) that `Launcher`, `ClipboardPopup`, `Settings`, `SettingsWindow`, `WallpaperPicker` set; `BarPill` uses `glassBarPanels` when `strong` (a whole look now; before only the tint differed), else `glassBar`. Every look has a Tint colour (Background for the default look until set). Not covered: the Classic layout's menus (`BarMenu`, opaque, no glass), the wallpaper overlay's neighbours (their own blur). **UI:** Theme › Glass has a "Widgets" section (kind `widgets`, `ThemeSchema.widget()`, drawn by `GlassWidgetRow.qml`): one line per widget with Default look / Own look; own adds a chevron, opens in place (picking Own opens it), closed shows "n changed"; the values an own look does not set are dimmed (`inherits` on the items, `SettingsRow.inherited`). The widgets' own pages have link rows (`ThemeSchema.glassLink`, type `link`, `LinkField.qml`: "Follows the default look" / "Own look, n values changed", "Edit glass ↗" sends `SettingsIndex.jumpRequested`, which `SettingsView` turns into `jumpTo`); links are not Theme values (`flatten` leaves them out). Window rules' "Default look" uses `Theme.glassDefault` (its tint too). **Migration** (`ThemeStore.migrate`): `glassBarLook` / `glassPanelLook` become `<group>.look`; an own `glassPanel` look is copied to the five panel widgets (else dropped); values equal to their (live) default are dropped. Checked in a scratch copy: the migration from an old file, live fallback (a default-look change reaches the values a widget does not set, not the one it sets), dropping a value set equal to the default, the widgets list, an own look opened by a jump, the links and their jumps, no warnings. **First deploy bug:** `Launcher.qml`, `ClipboardPopup.qml` and `SettingsWindow.qml` used `Theme` without `import qs.shared` ("Theme is not defined" at runtime, so their panels got no look and ignored every setting; qmllint only counts that as a warning), and `GlassListPanel` had a style with `id: look` next to its `look` property (an unqualified `look` meant the style). Fixed; `check.sh` now has an `imports` part that fails on it. Checked after the fix: a scratch launcher with an own look (blur 40, no tint, brighter) against the default, both open, clearly different, no warnings. NOT checked: the clipboard, the wallpaper window and overlay, notifications and the bar running with it (lint and build only), how the strong pills look with a whole look of their own.

**Default glass look (2026-11-20, same branch).** One global look on Theme › Glass ("Default look": `Theme.glassDefault`, a `GlassLook` with the same 12 parameters as `glassPanel`/`glassBar`; its defaults are the old panel look). `Theme.glassPanelLook` / `glassBarLook` ("default" or "own"; defaults: panels "default", bar "own") choose per element: `PanelGlassStyle` / `BarGlassStyle` take `Theme.panelGlass` / `Theme.barGlass` (the look in use: `glassDefault` or their own) (the bar's tint colour only with its own look, else Background). On the Panels and Status bar pages a "Look" choice; the own sliders are blocks with `showIf` (a block-level `showIf`, supported by `SettingsBlock` and `ThemeSchema.flatten`). Window rules: a rule of the app can have glass mode **"default"** (the default look plus its own `radius`, `taps`, `corner_radius`, `opacity`: `HyprlandStore.ownKeys`); a base rule with glass and a name can **follow the default look** ("Default look" button on its row; `HyprlandStore.follow`, stored with the rules' JSON as `follow`): `hyprland-settings.lua` then gets, before the app's rules, the same match with the base rule's own keys plus the default look, stored in the global `LucentGlassFollowers[<name>]` so that the Super+Alt+G bind in `hyprland.lua` switches it with the kitty rule. The JSON also keeps `look` (the default look it was written with); when the default look changes and something uses it, the file is written again (600 ms pause) and Hyprland reloaded. The **settings overlay** no longer blurs the desktop (the user's choice; `scrimBlurRadius` removed): `GlassScrim.blurred: false` keeps the veil in its plain mode, a tint of Background at `Theme.scrimDim` (Panels › Settings overlay › Desktop dim, default 0.35; 0 = the desktop as it is); the settings panel's own blur is `glassBlurRadius` like the other panels. `Theme.panelGlass` and `Theme.barGlass` are derived (not settings): the looks the panels and the bar really use after the default / own choice; read those (`Theme.barGlass.tint`, `.tintStrength`, ...), not `glassPanel` / `glassBar`, outside the style files. **Window-rule parameters are grouped** like the Theme pages: each entry of `HyprlandStore.glassParams` has a `block` (Blur, Tone, Rim, Light, Window), `paramBlocks` groups them in that order, and `GlassParamBlocks.qml` draws them (editable in `RuleCard`, read-only in the base rules). A base rule now opens on click (chevron) and shows its other effects and every glass parameter: the ones its `lucent_glass` leaves out show the PLUGIN's default (`def`, the Lucent README's table), dimmed, not the default look; with the default look followed, the look keys show the look's values (`HyprlandStore.effectiveParams`). The base file (`~/.config/hypr/hyprland.lua`, the deployed one: a rule added in the repo shows after `hms`) is watched and read again whenever the Window rules page is shown, and any `hl.window_rule` with `lucent_glass` (a string or `table.concat`) is parsed the same way, nothing is specific to kitty. The search field's paddings are equal (measured: capitals' middle 51 px, icon 51-51.5 px; the old bottom padding 5 put the text about 3 px high). Checked in a scratch copy (`XDG_CONFIG_HOME` and `HYPRLAND_SETTINGS_FILE` in a scratch dir, `HYPRLAND_INSTANCE_SIGNATURE` bogus so no reload reached the live Hyprland): the pages and choices, the generated Lua for a followed kitty rule and a default-look rule (`luac -p` ok, and `hyprland.lua`), a default-look change rewriting it. NOT checked: the generated rules in a real (nested) Hyprland, Super+Alt+G with the follower, the overlay's dim on the real desktop.

**Hyprland category: window rules with glass parameters (2026-11-17).** A second category in the settings app (`SettingsIndex.categories`, page `HyprlandPage.qml` in `SettingsView`'s `StackLayout`; it has no searchable settings: `sections: []`). Files: `HyprlandStore.qml` (singleton: the rules, validation, the Lua generator and parser, writing, reload, the base-config parser), `HyprlandPage.qml`, `RuleCard.qml` (one rule: header with enable switch, duplicate, delete; editor: name, match, glass), `ParamRow.qml` (a glass parameter: slider or colour, ↺ when set), `TextRow.qml`, `Segmented.qml`. **Where it writes:** `~/src/nix-config/home-manager/gui/hyprland/hyprland-settings.lua` (next to the source of `hyprland.lua`, like hyprmod's `hyprland-gui.lua`; env `HYPRLAND_SETTINGS_FILE` overrides it for tests). It is in `.gitignore` (`home-manager/gui/hyprland/hyprland-settings.lua`; note the older entry for `hyprland-gui.lua` points at a path that does not exist, so that file is tracked) and `hyprland.lua` `dofile`s it **at its very end**, so its rules come after the base config's. **No hms:** after a change (600 ms pause) the store writes the file and runs `hyprctl reload`, then reads `hyprctl configerrors` 800 ms later and shows the lines about this file (line number and message; `hyprctl reload` failing shows its error). **Checked in a headless nested Hyprland** (`AQ_BACKENDS=headless` still opened a small window on the host; start with `env -u HYPRLAND_INSTANCE_SIGNATURE`, kill the real `Hyprland` child by PID with `kill -9`, the PID file only holds the wrapper): a later rule overrides an earlier one for the same effect (both ways); `hyprctl reload` re-reads the file, re-applies rules to windows that are ALREADY OPEN (checked with a `tag` effect) and drops removed rules; `configerrors` reports unknown fields, wrong value types and syntax errors with file and line, but NOT an invalid regex or a bad `lucent_glass` string (the app validates regexes with JS `RegExp` and `tint` itself, and does not write such a rule); the Lua API has no way to list rules (no getter in `share/hypr/stubs/hl.meta.lua`), so the base config's rules are parsed from the text of `~/.config/hypr/hyprland.lua` (comments stripped, `hl.window_rule({...})` tables read; `lucent_glass` given as strings or `table.concat` is read back into parameters), only to list them read-only and to start an **Override** (a new rule with the same match and glass). The whole chain with the real plugin in the nested session: adding a glass rule from the app turned an open translucent window from Hyprland's blur to the plugin's tinted glass (stripe contrast 0.26 to 0.003), "Glass off" brought the blur back, disable/enable/delete applied live, and the app read its rules back from the file after a restart. **The data model:** a rule is `{id, name, enabled, match: {class, title, initial_class, initial_title, float: ""|"yes"|"no"}, glass: {mode: "inherit"|"custom"|"off", params}}`; the file holds the rules as Lua (`hl.window_rule({name, match, lucent_glass = "radius=14 tint=... "})`, inside `if io.open("/etc/hypr/plugins/liblucent.so")` because `lucent_glass` is unknown, an error, without the plugin) and, in a `--[====[ quickshell-settings ... ]====]` comment, the same rules as JSON, which is what the app reads (do not edit the file by hand). "No change" (inherit) and rules with nothing to match, a bad regex or a bad tint are not written (the card says why); "Glass off" writes `lucent_glass = "false"`, which switches the glass of a base rule off for those windows; custom writes only the parameters that were changed (the rest keep the plugin's defaults, shown dimmed; no parameter = `"true"`, a plain blur). The first rule of the list is written LAST, so the rule higher in the list wins when several match one window. The 17 parameters and their ranges are in `HyprlandStore.glassParams` (from Lucent's README table; the sliders use smaller ranges for some). Not covered on purpose (for now): other effects (float, size, opacity, ...), other kinds of rules, Hyprland options. NOT checked: clicking and typing in the page (all changes went through a test-only IPC hook that was not kept; the screenshots show the page), a first run on the live session (nothing here was run against the live Hyprland: the scratch app's reload target was a nested instance or a bogus signature), the `dofile` line in the deployed `hyprland.lua` (needs `hms`; the same lines were used in the nested config), the settings window form of the page, regexes that JS accepts and RE2 rejects (or the reverse).

**Glass look settings (2026-11-17; the layout of that time, Glass section with collapsible groups, was replaced 2026-11-20: see "Page structure").** The look settings are the parameters of `GlassStyle` / the Lucent plugin's glass, as `GlassLook`s: `Theme.glassDefault` and one per widget (see "Per-widget glass looks"): Frost, Tint (`TintStrength`), Brightness, Contrast, Saturation, Rim width (`Bevel`), Rim height (`Thickness`), Rim curve (`BevelProfile`, compositor glass only), Refraction, Index of refraction (`Ior`), Dispersion, Shine. They reach the glass through `shared/glass/ThemedGlassStyle.qml` (used by `GlassListPanel`, `LucentListPanel`, `NotificationCard`, `StatusBar.qml`/`BarPill.qml`) and apply live, for the compositor glass and the captured glass (except the rim curve). Not settings (fixed per element): corner radius, which edges have a rim, the panels' tint colour (= `Theme.background`), the light direction, `GlassStyle.alpha` / `opacity`. `backdropBlur` (legacy, unused) is not listed. A collapsed section (`ThemeGroup`) shows an accent "n changed" badge while closed, so a change cannot hide in it. Checked then (scratch copy, test-only IPC hook): jump into a closed group, the badge, search finding grouped settings, and that overrides in the scratch settings file visibly changed the overlay's glass. NOT checked: whether extreme values look good.

**Settings app** (`settings/`, config `qs -c settings`). **Two forms, one content** (added 2026-11-17, branch `feature/wallpaper-picker`): the full-screen OVERLAY (`Settings.qml`: a `GlassPopup` with the veil and a `GlassListPanel`, as described below; namespace `settings`, tag red 34 like the launcher, so do not open it together with the launcher) and a NORMAL WINDOW (`SettingsWindow.qml`: a `FloatingWindow` titled `Settings`, tiled by Hyprland like any window, with compositor glass through `LucentListPanel`, see `shared/glass/GLASS-WINDOWS.md`; no veil, no captured glass, no shadow of its own; opaque panel without the plugin; created in a `Loader` only while open, so it starts fresh; Super+C closes it like any window). What is inside (sidebar, search, pages, keys) is `SettingsView.qml`, used by both hosts (`glassOn` false = plain fills for the highlights; it asks the host to close with `closeRequested()`). The IPC target `settings` is in `shell.qml`: `toggle`/`show` = overlay, `toggleWindow`/`showWindow` = window, `hide` = both, `isOpen` = the OVERLAY only (the Super+C bind uses it; a window is closed by the compositor like any other). Opening one closes the other. The bar's gear button still opens the overlay. In the app launcher the user chooses which one an app row opens (section 9, "Launcher: overlay or window"). Checked (scratch copy of the deployed settings config, live session): the window (tiled, glass, same pages, category highlight), the overlay (veil, highlights, unchanged look), switching between them through IPC, `hide`, no crash report. NOT checked: keys, mouse and search in the window form (the content is the same code as the overlay's, but nothing was typed), a floating or resized window, Super+C on the window, a long run.
Files: `Settings.qml` (overlay host), `SettingsWindow.qml` (window host), `SettingsView.qml` (the content: sidebar, keys: Esc / Ctrl+C close, Up/Down categories), `ThemePage.qml` (the schema: sections and items; one entry per `Theme` value), `ColorField` (swatch, hex field, picker), `NumberField` (stepper for ints, slider for reals), `SwitchField`, `SettingsRow` (label, note, reset arrow), `ThemeStore.qml` (singleton that edits and writes). Store: `preview(key, v)` changes the value in this process only (drags), `commit()` writes (30 ms coalesced), `set` = both; a value equal to its default is removed from the file; `ThemeFromSettingsApp.ownWrites` makes the loader ignore reads of the app's own recent writes (a late file-watcher reload used to overwrite newer in-memory changes). Controls are opaque or outline-only (no translucent items over the glass, section 9). Opened by the bar's gear button (`status-bar/SettingsButton.qml`, runs `qs -c settings ipc call settings toggle`); started at login by `hyprland.lua` (`hl.exec_cmd("qs -c settings")`, needs a Hyprland restart or a manual start the first time) and by `reload.sh`.
Super+C: Hyprland swallows it (the app is a layer surface, not a window), so the bind in `hyprland.lua` asks `qs -c settings ipc call settings isOpen` and hides the app if it is open, else closes the focused window. Turning `Theme.glass` off at runtime: `GlassPanel.known` is `backdrop.ready && backdrop.glassEnabled` and `GlassBackdrop` clears `ready` when the glass goes off, so the panel becomes the plain tinted one at once (checked live with the file) and comes back with a fresh blur when it is turned on again; before this the last blur stayed on screen.
**Veil over the desktop.** While the overlay is open the desktop behind it is covered (`shared/glass/GlassScrim.qml`), so that it is clear that only the settings can be used and that a click elsewhere closes them (the full-screen `MouseArea` under the panel does that; the veil takes no mouse). Since 2026-11-20 it is NOT blurred (the user did not want the blur): `blurred: false`, a plain tint of Background at `Theme.scrimDim` (a `Shape` with the panel's rounded rectangle as an odd-even hole, `Shape.CurveRenderer`). `GlassScrim` can still be a blurred glass veil (one full-surface glass with a rounded hole, `GlassPanel.holeRect` / `holeRadius` in `glass.frag`, or the plugin's `holeRect`; not a second panel under the settings panel: two glass layers leave under 3% of the background). Lessons from that version: the captured glass cannot show the desktop sharp (the veil is 92% opaque, so recovering the picture divides the screenshot by 0.08, which turns smooth gradients into steps about 12 levels apart), hence the plain tint below 3 px of blur (`plainBelow`); the panel's edges must be on whole physical pixels (`GlassGeometry.alignedSize`) or an edge falling inside a pixel shows as a lighter line; `GlassTag` has `z: 1000` in `GlassPopup` so that the veil never covers the tag pixel. The settings panel's tint grows as its blur radius falls (`Theme.glassSettings.inUse.tintStrength` + up to 0.3 below 8 px) so that sharp text behind it does not show through. Not checked: a click outside (no way to click from here), multi-monitor.
**Blur radius applies live:** a `GlassBundle`'s blur passes are not live (`scheduleUpdate`), they were rendered only when a capture arrived (`process()`), so a new `Theme.glassBlurRadius` showed on the status bar only when the screen behind it changed (an idle bar: not until the next capture). `GlassBackdrop.onBlurRadiusChanged` now calls `GlassBundle.reblur()` on the shown bundle (the two blur passes from the settled background; deferred with `Qt.callLater` so the bundle's sigma has updated). Reproduced and fixed in a scratch copy with captures stopped (`qs -p ... ipc call glass setCapture false`): before, radius 40 to 2 changed the picture by 0.015 (RMSE, normalised), after a resumed capture by 0.069; after the fix 0.072 at once, and back to 40 gave the original picture again. Not run on the real status bar (it would need its settings file changed).
**Page buttons** (were section buttons): a category in `ThemeSchema` lists `actions` (ids of `ThemeActions.actions`), shown as `ActionButton`s in the page header: `restartBar` (Status bar) kills the bar process found from `hyprctl layers` (`namespace: statusbar`; not `pkill -f`, which would match the command itself) and starts `setsid -f qs -c status-bar` after 0.6 s, showing `Restarting…` for 3 s (if the bar is not running it just starts it); `testNotification` sends a notification over D-Bus (`busctl`). Expected, not checked: a bar restarted while the settings are open has no glass until they are closed (section 9). NOT run end to end (it restarts the real bar).
**Trackpad momentum:** `settings/KineticFlickable.qml` (a `Flickable`, used by `ThemePage`) takes the wheel events that carry a `pixelDelta` (two-finger touchpad scrolling; a mouse wheel has none and is left to the Flickable) with a `MouseArea` (`acceptedButtons: NoButton`), moves the content itself, and when no event has come for 60 ms (fingers up) glides on with the speed of the last ~100 ms (`glideTime` 0.35 s time constant, no glide below 150 px/s, max 8000 px/s); a new touch event or a drag stops it, the page ends stop it. Qt on Wayland gives no momentum, so it is done here. Checked with scripted events in a scratch copy (flick: glide distance about speed x 0.35 s with smooth decay; new touch stops it; slow scroll does not glide; flick past the top stops at 0). NOT checked with a real trackpad (no way to produce those events from here): whether the touchpad's events really arrive with a `pixelDelta` and reach the `MouseArea`, the feel (`glideTime`, `minGlideSpeed`), and whether the direction is right.
**Search** (deployed; only partly tested, see below). The settings definitions are in `settings/ThemeSchema.qml` (sections, items, `keywords` = synonyms); `SettingsIndex.qml` holds the categories and the search: all words must match, score = label (prefix 100, word start 80, substring 60) > synonyms (50/40) > property name (35/30) > section/category (25) > note (20), ties in page order. `SettingField.qml` picks the control by type (used by `ThemePage` and `SearchResults`). `Settings.qml`: a `TextField` above the page (it is the `GlassListPanel`'s `field`, highlight drawn by the glass); results replace the page while the query is not empty (the page stays alive). Results are grouped by category, the selected one first (titled `In Theme › Panels`), with the real controls (edit in place) and a jump button (`jumpTo`: selects the category, clears the search, `ThemePage.scrollTo(key)` scrolls and outlines the row for 1.4 s). `Only in <category>` chip (Tab) limits to the selected category; it shows only with more than one category. Sidebar rows show match counts while searching. Type-to-search: `Keys.onPressed` of the `keys` FocusScope only sees keys the focused item did not use; a text field uses all printable keys, so typing a value never searches; with nothing like that focused, a printable key (no Ctrl/Meta; AltGr allowed; not a leading space) goes into the search field. Esc: clears the search first, then closes. The empty search field shows only a magnifier icon (the hint "Search settings…" and the cursor only while it has focus). The field gives up focus on Esc, when the popup closes, and when the panel is clicked anywhere else while the field is empty (with a search going on it keeps the focus); choosing another category (click or Up/Down) clears the search and the `Only in` chip. The click part is a `MouseArea` (z 10000, over the whole panel) in `Settings.qml` looks at every press and sets `mouse.accepted = false`, so the press goes on to what is under it (a `TapHandler` on a parent, or on an overlay, did not work: scrolling lists took the press first, and a passive `TapHandler` overlay stopped the search field from getting its own click). Checked with synthetic clicks (`import QtTest`, `TestCase.mouseClick` in a scratch copy: a test hook that is not in the repo). Up/Down still switch category (which changes the group order). Adding a category: an entry in `SettingsIndex.categories` and a page in `SettingsView.qml`'s `StackLayout`. Tested in a scratch copy with `wtype`: type-to-search, results and counts, Esc twice, synonyms. Also tested in a scratch copy with a made-up second category (not in the repo): the grouping (`In Theme` first, then `In Other`), the `Only in` chip and Tab, match counts, and that choosing another category by click or Up/Down clears the search and the chip. Confirmed by the user on the deployed app: the jump button works, and typing in a hex value field does not start a search. Still not tested here: nothing known.
